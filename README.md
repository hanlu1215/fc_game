# fc_game — Linux 上的 FC / NES 模拟器

用 C++17 从零实现的任天堂 FC（NES）模拟器，CMake 构建，带图形界面和中文菜单。

**零外部安装依赖**：视频走 X11 + XShm，音频用 `dlopen` 加载系统已有的 ALSA，
中文用系统的 FreeType + Noto CJK 字体（找不到时自动降级为内置点阵字体 + 英文界面）。
编译运行不需要 `sudo` 安装任何东西。

## 编译

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j4
```

## 运行

```bash
./build/fc_game                  # 启动后是主菜单，可选「加载 ROM」
./build/fc_game SuperMario.nes   # 直接加载指定 ROM 并开始
FC_SCALE=4 ./build/fc_game       # 指定整数放大倍数（1–6，默认 3）
```

## 存档

存档按 ROM 的 **PRG CRC32** 归档，所以给 ROM 改名不会导致读档失效：

```
~/.local/share/fc_game/saves/<PRG-CRC32>/slot<N>.state
```

每个槽位的文件是带版本号和 CRC 校验的容器格式，加载时会比对当前卡带的
PRG 校验和，避免把存档读进错误的游戏。

带电池的卡带（如《塞尔达传说》）退出时会把 PRG RAM 自动写到 ROM 同目录的
`.sav` 文件，下次加载自动读回。

## 代码结构

```
src/
├── core/            模拟器核心（不依赖任何界面代码）
│   ├── cartridge.*  iNES / NES 2.0 解析、电池存档
│   ├── mapper.*     mapper 基类 + 0/1/2/3/4/7 实现
│   ├── cpu.*        6502 内核（官方 + 常用非官方指令）
│   ├── ppu.*        2C02，dot 级流水线
│   ├── apu.*        2A03，5 声道 + 帧计数器中断
│   ├── bus.*        CPU 内存映射、OAM DMA、open bus
│   └── console.*    组装整机，逐帧推进
├── state/
│   └── savestate.*  版本化的存档容器
└── ui/
    ├── platform.*   X11 窗口 + XShm 渲染 + 键盘
    ├── audio_out.*  dlopen 加载 ALSA
    ├── text.*       FreeType 中文渲染（带点阵降级）
    ├── font8x8.h    内置 ASCII 点阵字模
    ├── menu.*       文件浏览器
    └── main.cpp     应用主循环、界面、快捷键
tools/
└── fctrace.cpp      调用跟踪器 + 覆盖率驱动反汇编（开发辅助，见下）
```

设计上 `core/` 完全不认识界面——它可以被单独拿去做无界面运行或测试。
`fctrace` 也只依赖 `core/`，用的是 CPU 里那个零开销的调试钩子。

## 已修复的问题

开发过程中定位并修掉的四个 bug，按发现顺序：

**1. `BMI` 分支条件反了（`src/core/cpu.cpp`）**

```cpp
case 0x30: return branch(!flag(N));   // 错：这是 BPL 的条件
```

`BMI` 应在 N 置位时跳转。这是抄写时把 BPL 那行复制过来忘了改。BMI 是 6502
最常用的分支之一，条件反了会让《超级马里奥》整个控制流扭曲——游戏反复走进
"游戏结束→回标题画面"的分支，表现为**标题画面每 31 帧闪一次、大部分时间黑屏**。

**2. 精灵水平翻转未实现（`src/core/ppu.cpp`）**

OAM 属性位 6（水平翻转）在渲染时被完全忽略。SMB 让马里奥朝左时是把两个图块
互换后再给每块置翻转位，只画互换不翻转就会**左右半身各画各的、图像分裂**。

```cpp
// 图案字节 bit 7 是最左像素；翻转后要从 bit 0 读起
const u8 bit = (s.attr & 0x40) ? static_cast<u8>(offset)
                               : static_cast<u8>(7 - offset);
```

**3. APU 包络时钟速率错误（`src/core/apu.cpp`）**

包络（envelope）和三角波线性计数器被放在**每个 APU 周期**递减，而硬件是
**240Hz 的 1/4 帧**——相当于把音量包络加速约 3700 倍，瞬间衰减到 0。
表现为**金币等音效发不出来**。修正后输出峰值从 0.54 升到 0.68。
（帧计数器的 1/4 帧与 1/2 帧分工见 `clockQuarterFrame()` / `clockHalfFrame()`。）

**4. 非官方 RMW 指令标志位被覆盖（`src/core/cpu.h`）**

`rmw()` 辅助函数在 lambda 之后又调用了一次 `setZN(v)`，会覆盖
SLO/RLA/SRE/RRA/DCP/ISB 这六条组合指令最终 ALU 操作的标志。
SMB 不用这些指令，但其它游戏会用。修法是让 lambda 自己负责标志。

另外把存档格式版本号升到 2，使上述 bug 存在期间产生的存档无法再被读取。

## 调试工具：fctrace

一个 CPU 调用跟踪器 + **覆盖率驱动**的反汇编器，用于在没有源码的游戏里
回答"这段代码为什么没跑"。

```bash
cmake --build build --target fctrace -j4

./build/fctrace <rom> [帧数] --input right,jump \
    --calls [n]            # 调用最频繁的函数（JSR 目标）及其主要调用者
    --unreached            # ROM 里存在但从未执行的 JSR/JMP 目标
    --callers <addr>       # 谁调用了这个地址（含执行与否）
    --path <addr>          # 它执行时的调用栈（或报告"从未执行"）
    --listing <addr> [n]   # 反汇编
    --dump-cov <file>      # 导出 64KB 覆盖率位图，便于脚本二次分析
```

**关键设计**：反汇编由**实际执行过的 PC** 驱动。线性扫描一旦走进数据表就会
错位——手工读 ROM 最容易栽在这上面——而本工具在每个地址上都会检查它是否被
执行过，遇到未执行地址就向前找最近一个执行过的地址并对齐过去，把中间字节标成
`.byte ... (data)`，同时给每条指令附上命中次数：

```
B624: LDA  $0756   hits=745
B627: CMP  #$02    hits=745
B629: BCC  $B66E   hits=745
B62B: .byte $A5    (data)      <- 从未执行
```

## 已知问题：敌人与道具穿过地形（未解决）

**症状**：道具（蘑菇）和敌人（板栗仔）会穿过水管、砖块和地面，不受阻挡；
马里奥自己的碰撞正常。`?` 砖的破裂判定也因此错乱，火焰花不出现。

**已确认的事实**（用 `fctrace` 实测，900 帧）：

| 环节 | 地址 | 实测 |
|---|---|---|
| 方块缓冲地址表 | `$9BE1` | 缓冲在 `$0500` ✓ |
| 缓冲填充器 | `$94D3` ← 关卡列数据 `$06A1` | 填充正确，`$05B0` 起是 `54`(=地面砖) ✓ |
| `GetBlockBufferAddr` | `$9BE3` | 正确 ✓ |
| `BlockBufferCollision` | `$E3F8` | 正确，`LDA ($06),Y` 读到过 `54` ✓ |
| 物体水平移动 | `$BF14`（由 `$BF08` 调用） | 3410 次，正常更新坐标 ✓ |
| **物体对地形碰撞** | `$E1D0`（由 `$B6DE` 调用） | **0 次** ❌ |
| 带碰撞的移动路径 | `$B6BE` → `$B6D0`/`$B6DE` | **整段从未执行** ❌ |
| 实际生效的移动路径 | `$CABA` → `$CAC7` → `$BF07` → `$BF14` | 295 次，**不含碰撞调用** ❌ |

**结论**：物体被分派到了"只移动坐标、不调用方块碰撞"的那条移动路径上，
而带碰撞的那条路径是死的。碰撞底层本身工作正常。

**下一步线索**：`$B624` 是那道门，`LDA $0756 / CMP #$02 / BCC $B66E`，
其中 `$0756` = `PlayerStatus`（0=小、1=大、2=火焰），`$B66E` 又检查
`$074E`（`AreaType`）非零则返回。按字面读，1-1（`AreaType`=1）就该走死路，
但这与"游戏实际能跑"矛盾——**说明对这个门控的语义理解仍有偏差**，
应从"哪个上层调用者应当走 `$B6BE` 而非 `$CABA`"入手。

### 排查中走过的弯路（避免重复）

以下六处我判断错误并已逐一排除，记下来省得重走：

1. `$C0D2` —— 以为是物体碰撞，实为**敌人生成器**（写 `$16,X` = 敌人类型）
2. `$8A6B` —— 以为是 `GetBlockBufferAddr`，实为精灵构造例程
3. `$E398` —— 反汇编起点不是指令边界，整段解码错位
4. `$B624` —— 以为是主物体循环，实为受门控的子路径
5. `$0016,X` —— 是**敌人类型**（Goomba=`06`），不是方块类型；恒为 0 是空槽位，正常
6. 方块缓冲"从未被访问" —— 结论错误。读取是 `LDA ($06),Y` **间接寻址**，
   地址运行时才算出来，静态扫描 PC 看不到 `$0500`

另外注意：SMB 的 ROM 里大段代码（`$9CB4-$AEDB`、`$CACE-$D641`、`$F90A-$FFFF` 等）
在 1-1 从不执行，这**大部分是别的关卡/模式的代码和数据表**，属正常现象，
`--unreached` 的列表不能直接当作"缺失的调用"。

## 其它已知限制

- PPU 是 dot 级但 CPU 是逐指令步进的，不是完全周期精确。这会让少数对
  `$2002` 轮询时序极其敏感的游戏（如 Battletoads）出现偏差。
- MMC3 的扫描线中断用的是每扫描线一次的近似实现（对绝大多数游戏足够），
  使用 8×16 精灵的游戏可能会有偏差。
- MMC1 的"连续周期写入被忽略"这条硬件怪癖尚未实现，受影响的只有
  《Bill & Ted's Excellent Adventure》《Shinsenden》等极少数游戏。
- `$4014` OAM DMA 固定按 513 周期计，未实现 514 的相位情况（每帧最多差 1 周期）。
